## 靈感來源

我經常需要在手機、平板、開發板、筆電與主要 Windows 電腦之間移動檔案。常見方式都會增加步驟，例如上傳雲端、透過通訊軟體傳給自己、尋找傳輸線、安裝另一個客戶端，或為每台裝置設定共享資料夾。

**CatDrop** 的想法源自我為印刷店環境製作的區網收檔流程。我發現其中真正通用的需求是：

> 任何已連接到私人網路的裝置，都應能透過瀏覽器直接將檔案傳到我的主要電腦。

CatDrop 將這個想法變成小型個人生產力工具。我可以只在需要時建立臨時接收端點，也可以讓它常駐成為私人網路收件匣。

## 功能

CatDrop 在 Windows 電腦上執行本機 HTTP 檔案接收服務。同一可信任區網內的任何裝置，都可開啟上傳頁面、選擇一個或多個檔案並直接傳送，不需要外部雲端或裝置專用客戶端。

桌面控制台提供：

- 已驗證的 LAN URL、一鍵複製網址與按需產生 QR Code
- 目前位址失效時自動重新尋找 LAN 位址
- 與瀏覽器同步的上傳開放／暫停控制
- 可排序紀錄與多筆操作
- 繁體中文與英文介面
- 可設定儲存位置、檔案大小、開機啟動與支援格式

預設白名單模式會同時驗證副檔名與基本檔案特徵。CatDrop 會清理來源名稱與檔名、防止目錄穿越，並產生唯一儲存名稱而不覆寫既有檔案。可信任環境可選擇全格式模式，但介面會明確警告此模式停用特徵驗證。

## 建置方式

CatDrop 刻意維持小型架構：

- Python `http.server`：本機 HTTP 服務
- `sqlite3`：設定與上傳紀錄
- `tkinter`：Windows 控制台
- HTML、CSS、JavaScript：瀏覽器介面
- `qrcode`、Pillow：離線 QR Code
- PyInstaller 腳本：未來單檔 Windows 執行檔

桌面程式掌控伺服器生命週期；啟動 CatDrop 即啟動接收服務，關閉程式即停止服務。Windows mutex 防止多個程序競用同一連接埠。

瀏覽器會輪詢設定端點，使支援格式、預設語言與上傳狀態保持同步。暫停上傳時狀態頁仍可使用，但伺服器會以 HTTP 503 拒絕新上傳。

LAN 探測會從預設路由與 Windows 網卡收集 RFC 1918 IPv4 候選位址。在產生 QR Code 或複製網址前，程式會確認 CatDrop 首頁可透過候選位址回應；舊位址失效時自動切換。失敗會顯示固定錯誤碼並寫入輪替日誌。

Build Week 期間，我使用 **Codex 與 GPT-5.6** 檢索參考架構、拆解可驗證的小任務、實作功能、審查安全邊界、產生回歸測試、診斷 Windows 行為並維護 RADS。我仍在真實 Windows 環境中人工審查與驗證，不將生成程式碼視為自動正確。

## 遇到的挑戰

區網行為帶來最多邊界案例。`upload.local` 之類的主機名稱必須依賴路由器或 DNS；筆電切換網路或網卡後，網址也可能失效。因此 CatDrop 使用私人 IPv4，並在產生 QR Code 前驗證實際 HTTP 端點。

Windows Firewall 是另一個獨立邊界。服務可能在接收電腦本機正常，但手機仍無法連線，直到安裝私人網路防火牆規則。CatDrop 只回報它能在本機驗證的證據，不把本機成功誤稱為外部裝置可連線。

Multipart form-data 需要明確的 UTF-8 處理，才能正確接收繁中來源名稱與檔名。打包也要求區分臨時內嵌資源與必須持久保存的資料庫、日誌、接收檔案及 QR Code。

全格式支援需要明確安全決策。便利不代表任意檔案安全，因此預設仍是驗證白名單，寬鬆模式必須由使用者主動啟用並顯示警告。

## 值得肯定的成果

- 傳送裝置只需要瀏覽器
- 檔案留在可信任區網
- 接收服務有明確生命週期與暫停控制
- 重名檔案不會覆寫
- 正確處理繁中名稱與檔名
- 產生 QR Code 前驗證 LAN URL
- 內建環境診斷、輪替日誌、安裝腳本與 CI
- Windows 原始碼版本通過 37 項自動化測試、GUI smoke test 與真實 LAN URL／QR Code runtime 驗證
- Public GitHub repository 包含 MIT License 及完整繁中／英文文件
- GitHub Actions 在 Windows Python 3.11 與 Python 3.12 均通過

原始碼、安裝說明與驗證流程位於 [CatDrop 公開 repository](https://github.com/magicatJW/CatDrop)。

核心流程保持簡單：

> 啟動 CatDrop、分享或掃描已驗證的 LAN 位址、傳送檔案，完成後關閉 CatDrop。

## 學到的事

上傳請求只是可用傳檔工具的一部分。位址探測、伺服器狀態、防火牆、重名處理、檔名編碼、儲存位置與錯誤證據，都會影響流程是否可靠。

輕量工具仍需要清楚的信任邊界、持久決策、自動回歸測試，以及誠實呈現缺少的證據。本機 HTTP 成功只能驗證程式與位址，完整 LAN 與防火牆路徑仍需實體裝置證明。

Codex 在搭配小範圍與具體驗證時最有價值。持續維護 README、決策、狀態、索引與不可變任務報告，使專案能在不中斷決策脈絡的情況下恢復工作。
